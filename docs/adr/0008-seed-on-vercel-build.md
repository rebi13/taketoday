# 0008. 시드는 Vercel 빌드에서 마이그레이션 다음에 적용

- 상태: 승인
- 날짜: 2026-11-01

## 배경
구역 14개, 기본 미션 99개, 캐릭터 3종을 `seed/` JSON으로 관리한다. 사용자 미션이 템플릿 id를 참조하므로 DB에 들어가 있어야 앱이 동작하고, 기획서를 고치면 문장이 바뀌어 운영에도 반영돼야 한다. 바뀐 문장은 사용자 미션에도 반영하되, 사용자가 고친 완료 기준은 덮어쓰지 않아야 한다(기획서 8.2.1).

## 결정
`vercel.json`의 `buildCommand`를 `pnpm db:migrate && pnpm db:seed && pnpm build`로 둔다. `pnpm db:seed`는 JSON을 zod로 검증한 뒤 한 트랜잭션에서 upsert한다. 이름·완료 기준이 바뀐 템플릿은 `version`을 올리고, 그 템플릿을 켠 사용자 미션 중 `user_modified = false`인 것에만 새 문장을 쓴다. 시드에서 빠진 템플릿은 지우지 않고 경고만 낸다.

## 고려한 대안
| 대안 | 장점 | 단점 |
|---|---|---|
| 시드를 마이그레이션 SQL에 넣기 | 배포 단계가 하나 줄어든다 | JSON과 SQL 두 벌을 맞춰야 하고, 문장 하나 고칠 때마다 마이그레이션이 생긴다. 사용자 미션 반영 같은 조건부 갱신을 SQL로 쓰기 번거롭다 |
| 손으로 `pnpm db:seed` | 설정이 없다 | 잊기 쉽고, 코드가 기대하는 템플릿이 운영에 없을 수 있다 |
| 앱 시작·첫 요청 때 적용 | 배포 설정이 없다 | 서버리스 함수마다 실행돼 경합하고, 요청 시간에 DB를 더 깨운다(ADR 0004) |

## 결과
- 프리뷰 배포는 `develop`, 운영 배포는 `production`에 같은 시드가 들어간다. 시드가 검증에 실패하면 빌드가 멈춘다.
- 시드는 매 빌드마다 돌지만 바뀐 것이 없으면 쓰는 값이 같다. 빌드가 몇 초 늘어난다.
- 시드에서 템플릿을 빼도 DB에는 남는다. 정말 없애려면 사용자 미션을 어떻게 할지 정한 뒤 마이그레이션으로 처리한다.
- 아이템 시드(M4)도 같은 스크립트에 붙인다.

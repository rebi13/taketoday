# 0007. DB 마이그레이션은 Vercel 빌드에서 적용

- 상태: 승인
- 날짜: 2026-11-01

## 배경
Drizzle을 붙이면서 마이그레이션을 언제·어디서 DB에 적용할지 정해야 했다. 구현 계획 4장은 "운영 반영은 배포 파이프라인에서만"으로 정해 두었다. Neon은 `production`(운영)과 `develop`(프리뷰·로컬) 두 브랜치를 쓰고, Vercel 환경변수의 Production·Preview에 각각 연결돼 있다.

## 결정
`vercel.json`의 `buildCommand`를 `pnpm db:migrate && pnpm build`로 둔다. 운영 배포는 `production` 브랜치에, PR 프리뷰 배포는 `develop` 브랜치에 같은 마이그레이션을 적용한다. 로컬에서는 `pnpm db:migrate`가 `.env.local`의 `develop`에 적용한다. GitHub Actions CI는 `pnpm build`만 돌리고 DB에 접근하지 않는다.

## 고려한 대안
| 대안 | 장점 | 단점 |
|---|---|---|
| GitHub Actions에서 main 머지 시 적용 | 배포와 분리돼 실패 원인을 보기 쉽다 | DB 비밀값을 GitHub에도 둬야 하고, Vercel 배포와 순서를 맞추는 장치가 따로 필요하다 |
| 손으로 `pnpm db:migrate` | 설정이 없다 | 잊기 쉽고, 코드와 스키마가 어긋난 채 배포될 수 있다 |
| 앱 시작 시 적용 | 배포 설정이 없다 | 서버리스 함수마다 실행돼 경합하고, 요청 시간에 DB를 더 깨운다(ADR 0004) |

## 결과
- PR을 올리면 프리뷰 빌드가 `develop`에 먼저 적용해 보고, 머지하면 운영에 적용된다. 마이그레이션이 실패하면 빌드가 멈춰 배포되지 않는다.
- 마이그레이션은 새 코드가 배포되기 전에 적용되므로, 그동안 돌고 있는 이전 코드와도 맞아야 한다. 컬럼 삭제·이름 변경은 "추가 → 코드 전환 → 다음 배포에서 삭제"로 나눈다.
- 서로 다른 PR이 각자 마이그레이션을 만들어 `develop`에 적용하면 번호가 겹칠 수 있다. 혼자 개발하는 동안은 한 번에 PR 하나만 마이그레이션을 갖게 한다. 겹치면 `develop`을 `production` 기준으로 리셋하고 다시 적용한다.
- 함께 개발하는 사람이 생기거나 프리뷰마다 DB를 나눠야 하면 Neon 브랜치 자동 연동을 다시 본다.

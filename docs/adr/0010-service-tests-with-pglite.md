# 0010. DB 제약에 기대는 서비스는 PGlite로 테스트한다

- 상태: 승인
- 날짜: 2026-11-04

## 배경
M3 정산의 완료 기준은 "같은 날 정산을 두 번 불러도 한 번만 지급"이다. 이것은 `daily_settlements`의 (user_id, local_date) 유니크 제약과 트랜잭션이 지켜 주므로, 지금까지처럼 `server/domain`의 순수 함수 테스트만으로는 확인할 수 없다. 개발 환경에는 `.env.local`이 없어 Neon에 붙을 수도 없고, M1·M2 회고에서 "서비스 함수 테스트 방법을 정한다"를 M3 할 일로 남겼다.

## 결정
메모리 안에서 도는 Postgres인 PGlite(`@electric-sql/pglite`, 개발 의존성)에 커밋된 마이그레이션을 모두 적용하고, 서비스의 DB 처리 함수를 실제 SQL로 테스트한다. 테스트 DB는 `src/server/db/testing.ts`의 `createTestDb()`로 만들고, 앱 코드에서는 가져오지 않는다(`db/index.ts`로 내보내지 않고, ESLint는 `*.test.ts`에서만 이 파일을 허용). 세션(Auth.js)을 모르는 함수만 테스트하도록, 트랜잭션을 받는 부분(`settle-days.ts`)과 세션을 읽는 부분(`settlement.ts`)을 나눈다.

## 고려한 대안
| 대안 | 장점 | 단점 |
|---|---|---|
| PGlite (선택) | 접속 정보·가입 없이 로컬과 CI에서 바로 돈다. 실제 Postgres라 유니크·CHECK·외래 키·트랜잭션이 운영과 같게 동작. 테스트마다 새 DB라 서로 섞이지 않음 | Neon 드라이버와 타입이 달라 테스트 DB를 `Db`로 바꿔 넘긴다. 연결이 하나라 진짜 동시 접속(잠금 경합)은 재현하지 못한다 |
| 테스트용 Neon 브랜치 | 운영과 같은 Neon | CI에 DB 비밀값이 필요하고 느리다. Free 플랜 컴퓨트 한도를 쓴다(ADR 0004) |
| 프리뷰에서 손으로 확인 | 추가 작업 없음 | "두 번 불러도 한 번"을 손으로 재현하기 어렵고, 회귀를 막지 못한다 |

## 결과
- 정산(#24)과 이후 구매(M4)처럼 제약에 기대는 서비스를 테스트로 묶는다. 순수 계산은 계속 `server/domain` 테스트가 맡는다.
- 동시 요청은 "먼저 쓴 쪽만 들어가고 나머지는 건너뛴다"는 결과로만 확인한다. 실제 잠금 경합까지 봐야 하면 테스트용 Neon 브랜치를 다시 본다.
- 마이그레이션이 PGlite에서 돌지 않는 기능(확장 등)을 쓰게 되면 이 결정을 다시 본다.

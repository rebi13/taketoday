## 2. 계획대로 된 것

- **도메인을 순수 함수로 먼저 고정한 것.** `pickRecommendations`, `countPendingRewards`, `planCompletionReward`, `isChangeableDay`, `planMissionSchedule`, `planCriteriaChange`를 테스트와 함께 먼저 만들고 서비스·화면을 붙였다. 화면을 여러 번 고치는 동안 규칙은 한 번도 다시 손대지 않았다.
- **정산 규칙을 미리 공유.** "취소 제외 → 미션별 1건 → 상한 10"을 `countPendingRewards` 하나로 두어, 홈 적립 예정·기록 화면·완료 응답이 같은 수를 낸다. M3의 `settleDay`도 이 규칙을 그대로 쓰면 된다.
- **확장 대비.** 리스트 접근은 `canAccessList`만, `completions.user_id`는 수행자로만 쓴다(구현 계획 8장 체크리스트). 업적(2단계)도 지금 쌓는 기록만으로 계산할 수 있어 미리 만들 것이 없었다.

## 3. 계획과 달라진 것

### 바꾼 결정

| 무엇을 | 계획 | 실제 | 이유 |
|---|---|---|---|
| 서버 상태 | TanStack Query | 서버 컴포넌트 + Server Action + `useOptimistic` (ADR 0009) | 서버 컴포넌트가 읽은 값과 클라이언트 캐시가 둘로 갈리지 않는다. M1 켜기·끄기에서 이미 같은 방식을 썼다 |
| 추천 하루 고정 | daily_missions 저장만 | `recommendation_days` 표시를 따로 둠 | 추천이 0개인 날도 "만들었다"를 남겨야 낮에 다시 만들지 않는다. 동시 첫 요청도 기본 키로 한 번만 |
| 홈에서의 완료 취소 | T01 되돌리기만, P04는 기록 화면에서만 | 알림을 놓쳐도 완료한 카드의 P01 → P04로 취소 | 써 보니 알림이 사라지면 홈에서 고칠 길이 없었다 |
| P07 기한 지난 미션 | 홈에서 팝업 | 카드의 "정리" 버튼으로 연다. 끝내기 = 꺼 두기 | 열 때마다 팝업이 뜨면 다그치는 느낌(원칙 3) |
| 꺼 둔 미션과 오늘 추천 | 그날 추천에 남김(#19) | 아직 안 한 것은 빠짐 | P07 "이제 안 해도 돼요" 뒤에도 카드가 남아 어색했다 |
| 취소한 카드 모양 | 줄 긋기·흐리게 | 대기와 같은 모양 + 안내 문구 | 같은 날 다시 할 수 있는데 끝난 일처럼 보였다 |
| 카드 열 수 | 화면 폭(`mid:`) | 목록 칸 폭 컨테이너 쿼리(`@mid:`) | 두 칸 화면에서 좁은 목록 칸에도 2열이 되어 카드가 찌그러졌다 |

### 계획에 없던 것을 더한 것

- **#57 랜덤 닉네임**: 온보딩 입력 하나를 줄이려고 약관 동의 때 자동으로 준다.
- **#70 추천 밖 미션 하기**: 기획서 6.2 "추천 외에도 원하는 만큼 수행"이 있었는데 이슈로 옮기지 않았다. 써 보고 나서야 입구가 없다는 것을 알았다. 홈 "오늘 더 하기"(새 미션을 만들어 바로 넣기 포함)와 S12 "오늘 했어요"를 만들었다.
- **S13 나가기 확인 팝업**: 두 칸 화면에서는 목록이 옆에 있어 카드를 누르면 쓰던 내용이 사라졌다.
- **업적(2단계) 기획**: 써 보면서 나온 아이디어를 기획서 7.6에 남겼다. 연속 기록은 보류.

| 문제 | 원인 | 이후 |
|---|---|---|
| 상세에 들어갔다 오면 좁은 화면에서 목록이 사라짐 | Next 16(cacheComponents)이 떠난 화면을 `<Activity hidden>`으로 DOM에 남겨 두는데, CSS `:has([data-mission-detail])`가 숨은 상세까지 셌다 | 숨은 것(`style*=display`)을 빼고 판단. 수정 화면은 저장한 값으로 key를 바꿔 옛 입력이 남지 않게 |

## 5. M3에 가져갈 것

- 정산 `settleDay`는 `countPendingRewards`와 같은 규칙으로 만들고, 둘이 같은 결과를 내는지 테스트로 묶는다.
- 서비스 함수(트랜잭션) 테스트를 어떻게 할지 정한다. 정산은 "같은 날 두 번 불러도 한 번만 지급"을 DB 제약으로 보장하므로, 순수 함수 테스트만으로는 부족하다. 후보: 테스트용 Neon 브랜치, PGlite.
- 화면을 만들면 좁음·넓음 두 폭과 화면보다 긴 내용을 함께 확인한다.
- 이슈를 마칠 때: 변경 이력 한 줄, 화면 흐름이 바뀌었으면 screen-flow와 기획서 변경 이력.
- 기획서에 있는 기능이 이슈 할 일로 모두 옮겨졌는지 마일스톤 시작 때 한 번 맞춰 본다(#70 같은 누락 방지).
